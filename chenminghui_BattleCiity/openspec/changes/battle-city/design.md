## Context

本项目是鸿蒙应用开发课程的工程化作业，要求使用HarmonyOS DevEco Studio和ArkTS语言复刻1985年经典游戏Battle City（坦克大战）。项目目标API为API 10（HarmonyOS 4.0），使用纯原生Canvas 2D + ArkUI实现，不依赖第三方游戏引擎。采用OpenSpec规范驱动的开发流程管理需求和任务。

项目约束：
- 不允许使用第三方游戏引擎（Unity、Cocos2d-x等）
- 必须使用HarmonyOS原生Canvas 2D或ArkUI实现游戏渲染
- 目标帧率不低于30 FPS（理想60 FPS）
- 代码结构清晰、模块化，遵循ArkTS编码规范
- 使用中文编写OpenSpec规范文档

## Goals / Non-Goals

**Goals:**
- 实现完整的可玩游戏，包含所有核心系统（引擎、控制、AI、关卡、碰撞、得分、道具、UI）
- 至少实现10个关卡，覆盖头三关以上的完整玩法
- 稳定的60 FPS游戏循环
- 触摸友好的操作界面
- 至少3种敌人类型，4种能量道具
- 完整的菜单和UI流程（启动→主菜单→游戏→暂停→结束→存档）
- 模块化的代码架构，便于批改和维护

**Non-Goals:**
- 双人合作模式（超出当前范围，可作为后续扩展）
- 关卡编辑器（超出当前范围，可作为后续扩展）
- 在线排行榜（需要后端服务，超出当前范围）
- 网络多人对战（需要联网能力，超出当前范围）
- 音效系统（作业未明确要求，可选实现）
- iOS/Android跨平台（仅限HarmonyOS）

## Decisions

### 1. 渲染架构：Canvas 2D + ArkUI混合方案

**决策**: 游戏场景使用Canvas 2D绘制，UI层（菜单、HUD、按钮）使用ArkUI声明式组件。

**理由**: Canvas 2D提供像素级控制，适合游戏渲染；ArkUI提供原生组件样式和交互，适合菜单和HUD。通过Stack布局将Canvas和UI层叠放，实现游戏画面和UI的分离。

**备选方案**: 纯Canvas方案（UI绘制工作量大）、纯ArkUI方案（游戏渲染性能不足，粒子效果困难）。

### 2. 游戏循环：requestAnimationFrame驱动的固定时间步长

**决策**: 使用requestAnimationFrame作为驱动，结合固定逻辑时间步长（fixed timestep），渲染与逻辑更新分离。

**理由**: requestAnimationFrame自动适配屏幕刷新率，节省电量；固定时间步长确保碰撞检测和物理计算的一致性（避免帧率波动导致的行为差异）。

### 3. 实体系统：基类继承 + 组合模式

**决策**: 定义`GameEntity`抽象基类（位置、尺寸、速度、绘制、更新），具体实体（`PlayerTank`、`EnemyTank`、`Bullet`、`PowerUp`、`Terrain`）通过继承实现。共享行为通过接口/组合实现。

**理由**: Battle City实体类型有限且明确，继承方案简单直观。组合模式适用于共享行为（如可移动、可破坏、可收集）。

### 4. 碰撞检测：AABB + 网格空间分区

**决策**: 使用轴对齐包围盒（AABB）碰撞检测，配合网格空间分区优化宽相检测。

**理由**: Battle City中所有实体可近似为矩形，AABB检测简单高效。网格分区将26x26的瓦片地图划分为网格，减少O(n²)的碰撞检测到O(n)。

### 5. 地图与关卡：瓦片地图系统

**决策**: 使用26×26瓦片地图（每个瓦片16×16像素），关卡数据以JSON格式存储。瓦片类型包括：空地、砖墙、钢墙、水、森林、冰面、基地。

**理由**: 原版Battle City使用13×13大瓦片地图（每个大瓦片由4个小瓦片组成），采用26×26细粒度瓦片可兼容原版地图布局。JSON格式便于编辑和加载。

### 6. 敌人AI：分层状态机

**决策**: 使用分层有限状态机（HFSM）实现敌人AI。顶层状态：巡逻、追击、攻击、躲避；底层行为：随机移动、寻路到玩家、瞄准射击、避开子弹。

**理由**: 状态机可预测、可调试，行为丰富度足以模拟原版敌人的智能程度。不同敌人类型通过参数（移动速度、射击频率、巡逻模式）区分。

### 7. 数据持久化：HarmonyOS Preferences

**决策**: 使用HarmonyOS `@ohos.data.preferences` API存储游戏存档和最高分。

**理由**: Preferences是HarmonyOS提供的轻量级KV存储，适合保存关卡进度、最高分、设置等小量数据。无需引入数据库。

### 8. 项目模块结构

**决策**: 按功能领域划分模块，目录结构如下：
```
entry/src/main/ets/
├── engine/          # 游戏引擎（游戏循环、状态机、Canvas管理）
├── entity/          # 游戏实体（坦克、子弹、道具、地形）
├── system/          # 游戏系统（碰撞、AI、得分、道具管理）
├── level/           # 关卡系统（地图加载、关卡数据）
├── ui/              # UI组件（菜单、HUD、暂停面板、触摸控制）
├── util/            # 工具类（常量、数学工具、资源管理）
└── GameController.ets  # 游戏控制器（顶层协调）
```

**理由**: 按领域分层而非按技术分层，便于理解游戏功能。每个模块职责清晰，符合单一职责原则。

## Risks / Trade-offs

- **Canvas性能风险**: 大量实体同时渲染可能导致帧率下降 → 使用脏矩形优化（仅重绘变化区域），对象池复用子弹/粒子，必要时降至30 FPS
- **AI寻路复杂度**: 多敌人同时寻路可能造成性能尖峰 → 限制同时寻路的敌人数量（最多4个），使用简单贪心算法而非A*，缓存路径结果
- **触摸控制精度**: 虚拟十字键操控坦克可能不够精准 → 提供方向键+射击按钮布局，支持滑动手势辅助，可调整按键大小
- **内存占用**: 关卡切换时资源加载可能导致内存峰值 → 使用对象池管理实体，关卡切换时主动释放旧资源
- **ArkUI与Canvas通信**: 两套渲染系统需要同步状态 → 使用`@State`和`@Provide`/`@Consume`进行跨组件通信，游戏状态通过`GameController`统一管理
