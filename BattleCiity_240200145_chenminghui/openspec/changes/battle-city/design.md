## Context

Battle City 1985 是一款经典的自上而下坦克射击游戏。本项目需要在 HarmonyOS 平台上使用 ArkTS 语言完整复刻该游戏。当前项目为 DevEco Studio 6.02 创建的空白模板（API 22, HarmonyOS 6.0.2），采用 Canvas 2D 渲染方案实现游戏画面，ArkUI 组件实现 UI 界面。项目要求使用 OpenSpec 规范驱动的开发流程，所有代码需遵循 ArkTS 编码规范。

**约束条件**：
- 必须使用 HarmonyOS 原生 Canvas 2D 或 ArkUI，禁止使用第三方游戏引擎
- 目标设备为手机（phone），支持触摸操作
- 游戏帧率不低于 30 FPS，目标 60 FPS
- API 兼容性要求 API 22+

## Goals / Non-Goals

**Goals:**
- 实现完整的游戏循环和状态管理，达到 60 FPS 稳定运行
- 实现玩家坦克的 8 方向移动和射击控制（触摸操控）
- 实现 3 种以上敌人类型，具备智能 AI 行为（寻路、避障、射击）
- 实现 10 个以上关卡，包含砖墙和钢墙两种可破坏地形
- 实现高效的碰撞检测系统（坦克-子弹-地形-边界）
- 实现得分、生命值、关卡进度和存档系统
- 实现 4 种以上能量提升道具及其时效管理
- 实现完整的 HarmonyOS 原生风格 UI（主菜单、HUD、设置、暂停/结束界面、触摸控制）
- 头 3 关完整可玩

**Non-Goals:**
- 双人合作模式（加分项，非核心交付）
- 关卡编辑器（加分项，非核心交付）
- 在线排行榜（加分项，非核心交付）
- 音效系统（可使用占位资源，后续迭代优化）
- 网络对战功能

## Decisions

### 1. 渲染方案：Canvas 2D

**选择**: 使用 HarmonyOS Canvas 2D API（`@ohos.graphics.draw`）进行游戏画面渲染。

**备选方案**:
- ArkUI 组件方案：使用 Stack/Grid 布局 + 组件表示游戏对象。适用于简单 UI 级游戏，但 Battle City 需要实时渲染多移动对象和粒子效果，组件方案性能不足且开发复杂。
- XComponent + Native：性能最佳但开发复杂度高，不符合课程要求。

**理由**: Canvas 2D 提供像素级控制能力，支持批量绘制、离屏渲染，适合 2D 游戏场景，且符合 HarmonyOS 原生开发约束。

### 2. 游戏架构：ECS 风格模块化设计

**选择**: 采用面向对象的模块化设计，参考 ECS（Entity-Component-System）思想，将游戏对象（坦克、子弹、地形）设计为实体，系统层（渲染、碰撞、AI）独立处理逻辑。

**目录结构**:
```
entry/src/main/ets/
├── game/
│   ├── core/          # 游戏引擎核心（GameLoop, GameState, ResourceManager）
│   ├── entities/      # 游戏实体（Tank, Bullet, Terrain, PowerUp）
│   ├── systems/       # 游戏系统（Collision, AI, Score, PowerUp）
│   ├── data/          # 关卡数据、配置常量
│   └── renderer/      # Canvas 渲染器
├── ui/                # ArkUI 界面组件（Menu, HUD, Pause, GameOver, Controls）
├── pages/             # 页面入口
└── common/            # 工具类、类型定义、常量
```

**理由**: 模块化设计便于分工开发、单元测试和后续维护。各系统解耦，符合单一职责原则。

### 3. 游戏循环：requestAnimationFrame + 固定时间步长

**选择**: 使用 `requestAnimationFrame` 驱动渲染循环，配合固定时间步长（16.67ms, 60 FPS）进行逻辑更新。

**备选方案**:
- `setInterval`：不准确，可能造成帧率不稳定，且后台运行时仍消耗资源。
- 可变时间步长：简化实现但可能导致物理计算不稳定。

**理由**: `requestAnimationFrame` 与屏幕刷新率同步，提供最平滑的渲染体验。固定时间步长保证游戏逻辑的确定性。

### 4. 碰撞检测：AABB 包围盒

**选择**: 使用轴对齐包围盒（AABB）进行碰撞检测，结合网格空间分区优化。

**理由**: Battle City 中所有对象（坦克、子弹、砖块）均为矩形，AABB 是最精确且高效的检测方案。空间分区将地图划分为网格单元，减少不必要的碰撞检测对数。

### 5. 敌人 AI：有限状态机 + 简单寻路

**选择**: 每种敌人类型使用有限状态机（FSM）管理行为（巡逻、追击、射击、撤退），寻路采用基于网格的简单方向优先级算法。

**备选方案**:
- 行为树：更灵活但实现复杂，对于 Battle City 的简单 AI 需求过度设计。
- A* 寻路：计算开销大，对于小地图 + 动态障碍物场景不必要。

**理由**: FSM 清晰表达敌人行为逻辑，网格方向优先级寻路在原版游戏中已被验证有效。

### 6. 数据驱动关卡设计

**选择**: 关卡使用 JSON 数据文件定义地图布局（26x26 格，每格 16x16 像素），包含地形类型、敌人配置、玩家起始位置等信息。

**理由**: 数据驱动设计使关卡创建和修改无需改动代码，便于实现 10+ 关卡和后续扩展。

### 7. 状态管理：集中式 GameState

**选择**: 使用单例 `GameStateManager` 管理所有游戏状态（分数、生命、关卡进度、道具状态等），通过回调模式通知 UI 更新。

**理由**: 集中式状态管理保证数据一致性，简化存档/读档实现。

### 8. 触摸控制：虚拟摇杆 + 按钮

**选择**: 左侧虚拟摇杆控制移动方向，右侧射击按钮控制开火。

**理由**: 这种双拇指控制方案在移动端游戏中被广泛采用，提供精确的方向控制和即时射击响应。

## Risks / Trade-offs

| 风险 | 缓解措施 |
|------|----------|
| Canvas 2D 在低端设备上性能不足，帧率低于 30 FPS | 实现脏矩形渲染优化，仅重绘变化区域；使用离屏 Canvas 缓存静态地形 |
| 敌人 AI 行为过于简单或过于困难，影响游戏体验 | 通过参数化配置调整 AI 行为（射击精度、移动速度），保留调优空间 |
| 关卡数据格式不完善，后期需要大量修改 | 初期设计灵活的关卡数据 schema，支持版本号和扩展字段 |
| 触摸控制响应延迟或误触 | 实现触摸事件 debounce 处理，提供控制灵敏度设置选项 |
| 内存占用过高导致应用被杀 | 实现资源池化（Bullet Pool、Enemy Pool），控制同时存在的对象数量上限 |
| 屏幕适配问题（不同分辨率/比例设备）| 使用相对坐标系统，以游戏世界坐标为基础，渲染时变换到屏幕坐标 |
